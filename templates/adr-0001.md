## Contexte

Ce projet est amorcé avec le harness SaaS solo, en **profil minimal** (`harness-reference.md` §15.1, HRN-INFRA-009 — maturité L2–L3). Ce profil dégrade l'*implémentation* de plusieurs invariants, jamais les invariants eux-mêmes. HRN-INFRA-010 impose que chaque forme dégradée soit **écrite** : une dégradation non écrite est une dégradation non décidée, et elle se découvre le jour où l'on croyait la garantie acquise.

Cet ADR existe pour que cette liste soit signée une fois, ici, plutôt que relue dans un document de 864 lignes à chaque interrogation.

## Décision

### Formes dégradées retenues (§15.2)

Pré-remplies : ce sont les choix **déjà faits** par le harness. Ne modifier une ligne que si ce projet dévie réellement.

| Invariant | Forme retenue ici | Porteur |
|---|---|---|
| Journal append-only | historique Git + plans versionnés + notes de backlog, **explicitement déclarés comme le journal** | PROG-13 |
| Oracles branchés dans la boucle | V0–V3 déclarés dans la DoD de chaque plan et exécutés | PROG-10 |
| Plan revu avant exécution | gate humain explicite (« GO S-xxx ») sur un plan persisté | G-17, PROG-07 |
| Redaction des secrets | permissions d'outil + interdiction d'écriture + `.gitignore` | ENV-06, BOOT-07 |
| Modèle épinglé | couple modèle + effort **enregistré a posteriori** à la livraison | PROG-12, PROG-08 |
| Budgets | budget déclaré au plan, **constaté** à la livraison — arrêt humain, pas machine | PROG-14 |
| Budgets monétaires | coût **constaté** a posteriori, reporté dans `backlog.yaml` | PROG-14 |
| Évals sur changement de connaissance | évals de **routage** + canaris humains + linter du référentiel | EVAL-01, EVAL-04 |
| Replay bundle | **non exigible** en profil solo | — |

### Ce qui ne se dégrade à aucun palier

Trois règles, et le projet les tient sans exception : aucune tâche exécutée **sans oracle déclaré** ; aucun changement significatif exécuté **sans gate** ; aucun élément présenté comme **vérifié sans oracle passé**. Si l'une saute « parce que c'est du local », ce n'est plus un harness.

## Alternatives considérées

- **Profil plateforme** (§15 : sandbox microVM, run store, model gateway, replay) — rejeté : dimensionné pour du multi-tenant supervisé, sans rapport avec le coût d'un solo.
- **Aucun harness** (prompts au fil de l'eau) — rejeté : c'est le mode de panne que ce dépôt existe pour éviter (plan improvisé, ledger complaisant, règle métier inventée).

## Conséquences

- Le journal du projet **est** l'historique Git : aucune slice ne se termine sur un état non committé (PROG-13, DEL-01).
- Aucun arrêt dur machine sur les budgets : un dépassement se constate à la livraison. Un dépassement non constaté est le seul vrai échec (PROG-14).
- Le modèle n'étant pas épinglé avant exécution, la comparaison entre deux campagnes repose entièrement sur la session réelle déclarée à la livraison. Ne pas la déclarer supprime le seul substitut d'épinglage.
- Aucun run n'est rejouable à l'identique. En cas de comportement anormal, le diagnostic part des artefacts (plan, journal de vérification, commits), jamais d'un replay.

## Stratégie de migration / retour arrière

Passage à un palier supérieur : réviser cet ADR (statut `superseded`), ligne par ligne. La montée se fait par invariant, pas en bloc — et jamais avant que le palier courant soit mesuré en production (`harness-reference.md` §19).

Mise à niveau du harness lui-même : `/harness-upgrade` (BOOT-08), qui compare `HARNESS_VERSION` au référentiel source et applique le changelog règle par règle. Les dérogations décidées ici sont préservées : elles ne se réécrasent pas par copie en masse.
